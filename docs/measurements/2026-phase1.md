# Phase 1 measurements

Phase 1 measures two things that later decisions wait for. Both are indicators. Neither decides anything.

| What | It informs | State |
|---|---|---|
| Tool calling of the model, with `llm-smoke` | Whether the agent loop of phase 4 can run on the model | Pending the owner's run |
| Size of `ImageInventory` objects, with `inventory-load` | The storage gate of decision 0004 | Measured on kind, below |

## Tool calling of the model

**Pending the owner's run.** The tool is written and tested against a scripted server. It has not been run against a real endpoint, because that takes the owner's endpoint and API key.

The agent loop of phase 4 is a conversation in which the model calls tools. This is the go/no-go for it: a model that can't do that reliably can't run it.

Run it with the API key in the environment, and nowhere else:

```bash
VEXPLAIN_LLM_API_KEY=... go run ./cmd/llm-smoke --endpoint <url> --model <model>
```

The endpoint is the base URL of the API, such as `https://llm.example/v1`. It must be https: the client sends the key only over https, or to a loopback host. `HTTPS_PROXY` and `NO_PROXY` apply.

**What a run does.** A run has two turns, and passes only if both do:

1. The model gets a system message and a question about a Brotli package, with the tools `lookup_package` and `submit_answer`, and chooses (`tool_choice: auto`). It should call `lookup_package`, once, with arguments that are valid JSON.
2. The tool answers that call, and the model must call a tool (`tool_choice: required`). It should call `submit_answer`, with arguments that are valid JSON.

The tool makes 20 runs by default (`--runs`), one request at a time, with the request settings that a `ModelConfig` defaults to: a timeout of 60 seconds and a temperature of 0.2.

**What it prints, and the bar.** The last line is the score, and the exit code follows it:

```text
tool_call_ok=N/20 p50_ms=… p95_ms=…
```

- `tool_call_ok` is the number of runs that passed. The exit code is 0 for 18 of 20 or better, and 1 below that. Below that, stop and report to the owner, because the agent loop of phase 4 depends on it.
- `p50_ms` and `p95_ms` are the latency of one request, over every request of the runs, failed ones included, in milliseconds.
- A run that fails prints a line before the score, with the turn and the reason.

**The replay check.** It doesn't count towards the score. Some servers, vLLM among them, parse the arguments of the tool calls that a conversation replays, and answer 400 when they are not JSON. The tool replays one call with the arguments `{bad`, and prints one of:

| Line | Meaning for the agent loop (design section 6.6) |
|---|---|
| `bad_arguments_replay=accepted` | This endpoint takes malformed arguments in a replayed history. Replacing them with `{}` is still the safe choice for other endpoints. |
| `bad_arguments_replay=rejected (HTTP 400)` | One malformed call would fail the whole conversation. The loop must replace the arguments of a malformed call with `{}` in the history it replays. |
| `bad_arguments_replay=inconclusive (…)` | The request failed for another reason, so the endpoint's behaviour is unknown. Treat it as rejected. |

**Result.**

| | Value |
|---|---|
| Date, and the model | pending the owner's run |
| `tool_call_ok` | pending the owner's run |
| `p50_ms`, `p95_ms` | pending the owner's run |
| `bad_arguments_replay` | pending the owner's run |

## Size of ImageInventory objects

**These numbers come from one past export of running images, loaded on kind. They are an indicator, not a decision.** Decision 0004 is clear that neither kind nor a synthetic load can tell whether CRDs hold up. That takes a real cluster over time: real scan churn, rescans, and a normal week's write rate. The decision waits for that.

The export is real platform data, so it stays outside the repository, and this page holds no count, no total and no name from it. What it holds is what describes the data model of the operator: the size of one object, and how cost grows with the number of objects.

### Method

- `hack/inventory-load` makes one `ImageInventory` for every distinct image of the export, and one entry in it for every cluster that runs the image. Each entry has the namespace count, the workloads (the first 100 are listed), and the repository, as the operator writes them. It writes through `inventory.Store`, as the operator does.
- Nothing of a real image or cluster is used but its name. The digest of an image is made up, as the sha256 of the image string, and so is the ID of a cluster, as the sha256 of its name.
- `--scale=10` makes ten copies of every image. Copy 0 has the digest of the image itself, and copy `i` the sha256 of the image string with `#i` added. The copies are identical but for their digest, so the sizes of one object are the same at ×10 as at ×1. The second scale is there to see how totals and listing grow.
- The size of an object is the length of the JSON that encodes it as the API server returned it, managed fields included. This is what the operator's own metric `vexplain_inventory_object_bytes` records after a write, and it is close to what etcd holds.
- The cluster was a single-node kind cluster with the CRDs installed (`make install`) and the operator not running, because the operator would delete digests that no pod runs. The ×10 load came on top of the ×1 load.
- The listing time is `kubectl get imageinventories -o name`, the median of seven runs after one that was not counted.

To repeat it with an export of your own:

```bash
make install                                              # the CRDs only, and no operator
go run ./hack/inventory-load --csv <export> --scale=1     # prints the sizes at ×1
time kubectl get imageinventories -o name > /dev/null
go run ./hack/inventory-load --csv <export> --scale=10    # adds the nine missing copies
time kubectl get imageinventories -o name > /dev/null
```

### Size of one object

| Bytes | ×1 | ×10 |
|---|---|---|
| p50 | 1883 | 1884 |
| p95 | 3812 | 3812 |
| max | 67702 | 67702 |
| Objects above 512 KiB | none | none |

No object comes near the first trigger of decision 0004, an object above 512 KiB. The largest is about an eighth of it. Most objects are around 2 KiB.

### Growth from ×1 to ×10

| | Ratio ×10 / ×1 |
|---|---|
| Total bytes of all objects | 10.0 |
| `kubectl get imageinventories -o name` | 6.8 |

Ten times the objects take ten times the bytes, as they should. Listing grows more slowly than the number of objects: part of its time is the fixed cost of starting `kubectl` and reaching the API server.

Absolute listing times depend on the machine. On the machine of this measurement, a laptop with kind in a container:

| | ×1 | ×10 |
|---|---|---|
| `kubectl get imageinventories -o name`, median of seven | 0.111 s | 0.760 s |

### What this does not show

The other two triggers of decision 0004 are not measured here: a sustained write rate above 5 per second, and inventory objects above 10% of the database size of etcd. Phase 1 loads once, and has no rescans. Nor does it show how objects grow when more clusters, or more workloads per image, are involved than in this export. An entry lists at most 100 workloads, and an object holds at most 256 entries, so the schema bounds the size of an object, but the bound is well above anything measured here.
